# 契約と索引

ライブラリの機能を、ソースコードを読まずに引けるようにする仕組みを定める。
公開関数の docstring を契約の正本とし、そこから索引 `docs/api/` を生成する。

合格の基準は一つである。契約だけを読んだ agent が、ソースコードを開かずに
その関数を正しく呼べて、結果をどこまで信じてよいかが分かること。

状態：fixed 2026-11-25 Claude（あかげふの指示による新設）。

## 1. 原則：what は持ち主の場所に、参照は where で薄く

内容（what）は、その持ち主の場所に 1 回だけ書く。ほかの場所は、名前とリンク
（where）だけで指す。同じ内容を二か所に書かない。

| 内容 | 持ち主の場所 |
|---|---|
| 対象の定義、番号付きの条件 | その対象の仕様ページ（`docs/specs/`） |
| 規約（向き、符号、番号付け、名前） | 規約ページ（`docs/conventions/`） |
| 演算の契約 | その演算の docstring |
| 出典 | [出典コメントの規則](../../../../docs/COMPUTATIONS.md#source-reference-comments)が定めるスコープ |

契約は、定義・条件・規約の本文を写さない。条件は番号（C1 など）で、規約は
項目名で呼び、持ち主のページへのリンクを添える。持ち主のページに書かれて
いない定義や規約が契約に必要になったら、先に持ち主のページへ書く。

## 2. 契約

契約は、公開関数の docstring である。公開関数とは、`Topology` とその
サブモジュールが export する関数を指す。言語は英語とする（ライブラリの
docstring の言語）。

節はこの順に置く。「必須」の節を欠く docstring は、索引で `incomplete` と
表示される。

| 節 | 必須 | 内容 |
|---|---|---|
| シグネチャ行 | 必須 | `name(arg::T, ...; kw) -> ReturnType`。戻り値の型を必ず書く |
| 要約 | 必須 | シグネチャ行の次の段落の 1 文目。数学の対象として何を返すかを 1 文で書く。索引の 1 行はこの文をそのまま使う |
| `# Arguments` | 必須 | 引数の型と前提。前提は条件の番号で書き、仕様へのリンクを添える。前提ごとに、関数が検査するか、呼ぶ側が保証するかを書く。検査する前提には、破れたときの例外の型とメッセージが伝える内容を書く。呼ぶ側が保証する前提には、破れたときに何が保証されなくなるかを書く |
| `# Returns` | 必須 | 戻り値の型と、各フィールドの意味 |
| `# Guarantees` | 必須 | 番号付きの事後条件。実装を知らずに検査できる形で書く。この番号は、その保証を検査するテストの名前に入れる。保証ごとに確認状態を付ける（2.1）。引数を書き換えるかどうかも、保証の一つとして書く |
| `# Conventions` | 該当時 | 出力が依存する選択の名前と、規約ページの項目へのリンク |
| `# Not guaranteed` | 該当時 | 呼ぶ側が誤って当てにしやすい点 |
| `# Complexity` | 該当時 | 入力の大きさに対する計算量 |
| `# Sources` | 該当時 | 出典がこの関数のスコープにあるときの `cf:` 行。外側のスコープ（型、ファイル先頭）の出典は繰り返さない |
| `# Examples` | 必須 | 値の分かっている最小の例。`jldoctest` の形で書く。出力は実行して得た値だけを書く |
| `See also` | 該当時 | 次に呼ぶ関数。たとえば π₁ の表示を返す関数は、アーベル化して H₁ を返す関数を指す |
| `Role:` 行 | 必須 | docstring の最後の行。役割を 1 語で書く |

`Role:` の語は次の 8 つである。索引は、この語でメソッドを分けて並べる。

| 語 | 意味 |
|---|---|
| `construct` | 対象を作る |
| `condition` | 対象が条件を満たすかを判定する |
| `access` | 対象の構成要素を取り出す |
| `invariant` | 対象の不変量を計算する |
| `move` | 対象を同じ種類の対象へ変形する |
| `convert` | 対象を別の種類の対象へ変換する |
| `draw` | 対象を描く |
| `other` | 上のどれでもない |

役割は呼ぶ側から見て決める。`construct` は、引数に登録された対象を取らない
ものに限る。登録された対象を受け取って別の構造を返すものは、`convert`、
`access`、`invariant` のどれかである。

実装の手順（どの順にたどるか、どのデータ構造を使うか）は、契約に書かない。
契約を書いた経緯（どのテストから値を取ったか、誰が確かめたか）も書かない。

### 2.1 保証の確認状態

`# Guarantees` の各項目は、末尾に角括弧で確認状態を持つ。状態の語は、
[セッション契約の証拠の状態](../../../../AGENTS.md#evidence-and-communication)を
そのまま使う（fixed 2026-11-25 Claude、規則 a）。

| 状態 | 契約での意味 | 角括弧に添えるもの |
|---|---|---|
| `proved/literature` | 出典が、その主張を前提と規約まで含めて述べている | その `cf:` 行が指す鍵と位置 |
| `proved/agent` | AI agent の証明か、実装から従う論証がある | 証明の記録へのパス。実装から直ちに従う場合は `by construction` |
| `proved/owner-checked` | あかげふが証明を確かめた | 証明の記録へのパス |
| `verified-computationally` | テストか検査が、有限の範囲で確かめている | テストのファイルと、確かめた範囲（例の数、パラメータ） |
| `unverified` | 引き継いだ主張で、確かめた裏付けが無い | 何が未確認か |
| `open` | 成り立つかどうかが決まっていない | 何が決まっていないか |

書き方の例：

```text
1. `generator_count == 2n` for a graph with `n` true vertices. [proved/agent: by construction]
2. The result presents the fundamental group of the closed manifold of `graph`.
   [open: identification of the raw edge presentation with the spine's fundamental group]
3. `free_rank` and the factors agree with `cellular_homology` on the registered
   closed examples. [verified-computationally: test/ograph_invariants.jl, 9 examples]
```

有限の例で確かめただけの主張を、`proved` の状態にしない。`unverified` と `open` の
保証は、何が確立していないかを `# Not guaranteed` にも書く。確認状態を持たない
保証がある契約は、索引で `incomplete` と表示される。

雛形：

````julia
"""
    name(x::T; kw=default) -> R

One sentence stating what is returned, as a mathematical object.

# Arguments
- `x::T`: ... Requires C1–C3 ([spec](../specs/<page>.md#<anchor>)).
  Checked: throws `ArgumentError` naming the violated condition.
- `y::U`: ... Requires <condition>. Caller's responsibility: not checked;
  guarantee 2 does not hold when it fails.

# Returns
`R` with fields ...

# Guarantees
1. ... [proved/literature: [[<key>#^<anchor>]] <locator>]
2. ... [verified-computationally: test/<file>.jl, <scope>]
3. `x` is not modified. [proved/agent: by construction]

# Conventions
- <item name>: [<convention page>](../conventions/<page>.md#<anchor>)

# Not guaranteed
- ...

# Complexity
O(...).

# Sources
cf:[[<key>#^<anchor>]] <locator> — <what was taken>

# Examples
```jldoctest
julia> ...
...
```

See also [`other`](@ref).

Role: invariant
"""
````

## 3. 対象の登録簿

ドメインの対象（o-graph、Heegaard code など）と Julia の型の対応を、
`docs/objects.toml` に書く。索引は、対象の名前から引く。

```toml
[o-graph]                      # 索引のディレクトリ名になる
name = "o-graph"               # 人が読む名前
types = ["TypeA", "TypeB"]     # この対象に属する型。部分型も属する
specs = ["docs/specs/<page>.md"]              # 対象の定義を持つ仕様ページ
conventions = ["docs/conventions/<page>.md"]  # 対象の規約ページ
sources = ["src/<file>.jl", "src/<dir>/"]     # 省略可。型で決まらない関数の帰属先
```

登録簿が持つのは where だけである。対象の定義は書かない。export される型は、
どれか一つの対象に属させる。属する対象が決まらない型は、索引の `GAPS.md` に
出る。

`sources` は、型では所属が決まらない関数のための受け皿である。引数にも戻り値にも
登録された型が現れない公開関数は、定義されたソースファイルが `sources` に
挙がっている対象に属する。型で所属が決まる関数には、`sources` は効かない。
一つのソースファイルは、一つの対象の `sources` にだけ書く。どの対象の
`sources` にも無いファイルの関数は、`unassigned/` に残る。

## 4. 索引 `docs/api/`

索引は生成物であり、手では編集しない。引く深さは 3 段である。

```text
docs/api/
  INDEX.md               対象の一覧。1 対象 1 行
  SOURCES.md             文献の鍵からの逆引き
  SPECS.md               仕様・規約の節からの逆引き
  GAPS.md                契約の欠けの一覧
  <object>/
    INDEX.md             その対象のメソッドの一覧。1 メソッド 1 行
    <function>.md        契約の全文
```

### 4.1 `INDEX.md`（対象の一覧）

1 対象 1 行で、名前、型、メソッドの数、契約を持つメソッドの数、その対象の
`INDEX.md` へのリンクを書く。

### 4.2 `<object>/INDEX.md`（メソッドの一覧）

先頭に、対象の名前、型、仕様ページと規約ページへのリンクを置く。その下に、
`Role:` の語ごとの見出しでメソッドを並べる。

- 1 行に書くのは、シグネチャ（`name(args) -> ReturnType`）、要約の 1 文、
  契約のファイルへのリンクの三つである。保証、規約、出典、例は書かない。
- 一覧のシグネチャは短縮形で書く。位置引数は先頭の 4 個までを書き、残りは
  `…` とする。キーワード引数があるときは `; …` とだけ書く。型名のモジュール
  修飾は省く。完全なシグネチャは契約のファイルに書く。
- 契約に戻り値の型が無いときは、`-> ?` と書く。
- docstring の無いメソッドは、`methods` から得たシグネチャと `[no contract]`
  を書く。必須の節を欠くメソッドは `[incomplete]` を添える。欠けた節の名前は、
  契約のファイルと `GAPS.md` に書く。
- 一つの関数が複数のシグネチャに docstring を持つときは、シグネチャごとに
  1 行を書く。
- 読み込まれたメソッドを持つ関数では、どのメソッドにも選ばれなかった宣言の
  docstring から、独立した行を作らない。同じ関数が二つの対象に別の文面で
  現れることを防ぐためである。その docstring は契約のファイルには載せる。

メソッドが対象に属するのは、引数の型か、シグネチャ行の戻り値の型が、その
対象の型（部分型を含む）であるときである。上位の型に定義されたメソッドは、
下位の型を持つ対象の一覧にも出す。

### 4.3 `<object>/<function>.md`（契約の全文）

1 関数 1 ファイルで、ファイル名は関数名とする。内容は次のとおり。

- docstring の全文。
- 継承した出典。関数、型、ファイル先頭の順にたどり、外側のスコープにある
  `cf:` 行を、スコープの種類を添えて書く。
- 定義の位置（ファイルと行）。
- この関数を一覧に載せている、ほかの対象へのリンク。

複数の対象に属する関数のファイルは、最初の引数が属する対象のディレクトリに
置く。引数がどの対象にも属さないときは、戻り値の対象のディレクトリに置く。
ほかの対象の `INDEX.md` は、そのファイルへリンクする。

一つの関数のメソッドが別々の対象を選ぶときは、最も多くのメソッドが選ぶ対象の
ディレクトリに置く。同数のときは、ディレクトリ名の順で先の対象に置く。
一つの引数の型か戻り値の型が複数の対象に属するときも、ディレクトリ名の順で
先の対象を選ぶ。

### 4.4 `SOURCES.md`（逆引き）

文献の鍵ごとに見出しを置き、その鍵を出典とするメソッドを 1 行ずつ並べる。
行の形は 4.2 と同じである。継承した出典による行には、スコープの種類を添える。
鍵の書式が出典コメントの規則に合わない出典（鍵の無い著者名や arXiv 番号）は、
末尾の見出しにまとめて出す。

契約は定義や規約を写さずに仕様の節へリンクするので、文献を引いているのが
仕様の節だけ、という場合がある。その経路も逆引きに出す。契約が仕様ページか
規約ページの節にリンクし、その節が文献の鍵を引いているとき、その鍵の見出しの
下に、メソッドの行を `via <ページ>#<節>` を添えて出す。鍵の下の行は、次の二つに
分けて並べる。

- **直接の出典**：関数、型、ファイル先頭の `cf:` 行による行。
- **仕様を介した依存**：仕様か規約の節を経由する行。経由した節を必ず書く。

帰属は節の単位で行う。節とは、リンクの錨が指す見出しから、同じ深さかそれより
浅い次の見出しの手前までである。ページのほかの節が引く文献を、そのメソッドに
帰属させない。錨の無いページへのリンクは、文献の帰属を生まない。

見出しの直前に置かれた明示の錨（`<a id="...">`）は、その見出しの別名として扱う。
段落を指す明示の錨は節を持たないので、文献の帰属を生まない。そのリンクは
`SPECS.md` には載り、`GAPS.md` の「解決できない参照」に「節の無い錨」として出る。
契約が指す先は、見出しを持つ節にする。

### 4.4.1 `SPECS.md`（仕様からの逆引き）

仕様ページと規約ページの節ごとに見出しを置き、その節へリンクしている契約の
メソッドを 1 行ずつ並べる。行の形は 4.2 と同じである。見出しはページのパスと
節の錨で書き、ページ、節の順に並べる。錨の無いリンクは、ページの見出しの下に
出す。条件の番号や規約の項目から、それを前提とするメソッドへ戻れる。

リンク先のページか錨が存在しないときは、その行を `GAPS.md` の「解決できない
参照」に出す。

### 4.5 `GAPS.md`（欠けの一覧）

契約の無い公開関数、必須の節を欠く公開関数、どの対象にも属さない公開関数、
どの対象にも属さない export された型を並べ、それぞれの数を先頭に書く。
索引に載せない export（4.7）と、この仕様が置き場所を定めていないものも、
それぞれ見出しを立てて名前を並べる。

保証の確認状態（2.1）ごとの数も先頭に書く。状態が `unverified` か `open` の保証は、
関数名と保証の番号と角括弧の中身を、見出しを立てて並べる。数学的な裏付けの
欠けを、ここから拾える。

### 4.6 出力の決まり

同じ入力からは、同じバイト列を生成する。並びは名前の順とし、時刻、絶対パス、
実行環境に依存する値を書かない。コミットごとの差分が、契約の増減を示す。

### 4.7 境界の扱い

- **どの対象にも属さない公開関数。** 型でも、登録簿の `sources`（3 節）でも対象が
  決まらない関数は、予約のディレクトリ `docs/api/unassigned/` に置く。
  `unassigned/INDEX.md` は 4.2 と同じ形で、契約のファイルもそこに置く。これらの
  関数は、すべての数に入る。契約に戻り値の型が書かれてそれが登録された型で
  あるか、定義ファイルが対象の `sources` に加われば、次の生成でその対象へ移る。
- **引数の型の数え方。** 型の無い引数と `Any` の引数は、対象への所属を決めない。
  `Union` と、型引数に登録された型を持つ入れ物（`Vector{T}` など）は、その中の
  型で数える。上位の型は、`Any` を除いて数える。
- **export された型。** 型の docstring は、その構成子の契約として扱う。ファイル名は
  型名とし、その型が属する対象のディレクトリに置く。役割は docstring の `Role:`
  行を使い、その行が無い場合だけ `construct` を既定値とする。役割の選択は §2 に従う。
- **索引に載せない export。** マクロと定数は索引に載せず、`GAPS.md` に名前を並べる。
  ほかのモジュールが持つ関数にライブラリが足したメソッド（`Base.show` など）は、
  索引の対象外である。
- **シグネチャ行の無い docstring。** シグネチャは `methods` から取り、
  `[incomplete: signature, …]` と表示する。要約は、docstring の最初の段落の
  1 文目を使う。
- **メソッドを持たない公開関数。** 宣言だけがあり、読み込んだ時点でメソッドを
  持たない関数は、`name(...)` を 1 行として `unassigned/` に置く。
- **拡張がメソッドを供給する関数。** ライブラリが宣言し、`ext/` の拡張がメソッドを
  供給する関数の契約は、宣言に付ける。生成のために任意の依存パッケージを読み込む
  ことはしない。拡張が読み込まれていなければ、上の「メソッドを持たない公開関数」
  として扱い、契約のシグネチャ行から所属を決める。読み込まれていれば、この
  ライブラリの `ext/` に定義されたメソッドも索引に載せ、型による所属の規則を使う。
  こうした関数の例は `jldoctest` にせず、拡張を読み込む `using` の行から始まる
  `julia` のコードブロックで書く。例の検査の対象にはならないので、その保証の
  確認状態に、検査が走らないことを反映させる。
- **外部の docstring の中の参照。** export し直した束縛の docstring にある、索引に
  無い名前への参照は、表示の文字列をそのままコードとして残し、`GAPS.md` の
  「解決できない参照」に記録する。
- **戻り値の型の無い契約。** `incomplete` として数える。「仕様が置き場所を定めて
  いないもの」には入れない。
- **リポジトリの外に定義を持つメソッド。** 定義の位置は、パッケージ名とファイル名
  と行で書き、リンクは付けない。
- **ほかのパッケージの束縛を export し直したもの。** docstring の持ち主はその
  パッケージであり、このライブラリでは契約を書けない。索引には載せ、一覧の行に
  `[external: <パッケージ名>]` を添える。契約の完全・不完全の数には入れず、
  `GAPS.md` に見出しを立てて名前を並べる。
- **定義の位置の取り方。** メソッドが読み込まれたときの位置（`method.file` と
  `method.line`）を使う。
- **名前の衝突。** 一つのディレクトリの中で、別の関数が同じ名前を持つときは、
  どちらのファイル名も `<Module>.<function>.md` とする。
- **ファイル名に使えない文字。** 関数名のうち Windows のファイル名に使えない文字は、
  パーセント符号化する。
- **この仕様が定めていない場合。** 生成スクリプトは、その項目を `GAPS.md` の
  「仕様が置き場所を定めていないもの」に出し、ほかの項目の生成を続ける。
  独自の規則で置き場所を決めない。

## 5. 生成

生成は `scripts/make_api.jl` が行う。リポジトリのルートから、常駐の Julia を
通して実行する。

```sh
sh lib/topology.jl/test/client.sh --exec lib/topology.jl/scripts/make_api.jl
```

スクリプトは `docs/api/` の全体を作り直し、今回書かなかったファイルを
`docs/api/` から取り除く。docstring と型の情報は、読み込んだ `Topology` から
Julia 自身の機能（`names`、`methods`、`Base.Docs`）で取る。ソースコードの
独自の構文解析は、ファイル先頭の `cf:` 行を読む用途に限る。
これに加え、4.4 と 4.4.1 の逆引きのために、`docs/specs/` と
`docs/conventions/` の Markdown ページから見出し、錨、文献の鍵を読む。
この二つのファイル読み取りを除き、docstring や型をソースファイルから取り直さない。

生成は、docstring か登録簿を変えたコミットの前に回す。生成物と docstring の
食い違いを検査するテストは置かない（あかげふの指定、2026-11-25）。

契約の例は、`scripts/check_api_examples.jl` で実行して確かめる。このスクリプトは、
読み込んだ `Topology` の docstring から `jldoctest` の塊を取り出し、塊ごとに新しい
モジュールで入力を評価して、書かれた出力と実行の出力を比べる。食い違いがあれば
一覧を出して失敗する。引数に名前の一部を渡すと、その名前を含む束縛だけを確かめる。

```sh
sh lib/topology.jl/test/client.sh --exec lib/topology.jl/scripts/check_api_examples.jl
```

例を書いた者が Julia を実行できないときは、例を提案として書き、契約を受け入れる
側がこのスクリプトを通す。通っていない例を持つ契約は、受け入れない。

## 6. 引き方

1. 対象を探す：`docs/api/INDEX.md` を読む。
2. メソッドに当たりを付ける：`docs/api/<object>/INDEX.md` を読む。
3. 契約を読む：`docs/api/<object>/<function>.md` を読む。
4. 語から探す：`rg -l "<語>" lib/topology.jl/docs/api`。当たったファイルの名前が
   関数名である。条件の番号、型の名前、文献の鍵でも同じように引ける。
5. 文献から探す：`docs/api/SOURCES.md` を読む。仕様の節を経由する依存も載っている。
6. 仕様の節、条件、規約の項目から探す：`docs/api/SPECS.md` を読む。

ソースコードを読むのは、契約が無いときと、契約と挙動が食い違ったときに限る。
そのどちらも欠けであり、契約を書くか直して閉じる。

## 7. 維持

契約と索引は、次の決まりで育て続ける。

- **変更と同じ区切りで直す。** 公開関数を足す、挙動を変える、docstring を変える
  作業は、同じ区切りで契約を直し、索引を生成し直す（5 節）。契約の無い公開関数と
  不完全な契約は、生成のたびに `docs/api/GAPS.md` に現れる。
- **`GAPS.md` が品質の作業一覧である。** 数を先頭に持ち、契約の欠け、`unverified` と
  `open` の保証、解決できない参照を並べる。手の空いた作業は、ここから取る。
  `unverified` と `open` の保証は、何を、どの出典と、どの例で比べれば確立するかを
  角括弧に書いてあるので、それを実行して状態を上げる。
- **食い違いは持ち主のページに残す。** 仕様・テスト・挙動の食い違いは、仕様か規約の
  ページに `bug:` の行で、未定の点は `question:` の行で書く。直したら状態を
  括弧に書き（`bug[fixed <日付>]:`）、行は消さない。
  `rg -n "^\s*(?:[-*]\s+)?(bug|question)(\[[^\]]*\])?:" docs` で一覧できる。
- **確定の判定は新しい Julia で行う。** 常駐のサーバーは書き換え前の docstring を
  持ち続けることがある。受け入れるときは、長時間用の段で生成と例の全件検査を
  回す（`sh lib/topology.jl/test/client.sh --long --limit 30 --exec <生成と検査を続けて呼ぶスクリプト>`）。
- **契約を使って困ったら、契約を直す。** 契約を読んでもソースを開く必要があった
  ときは、その箇所が欠けである。要約、前提、戻り値、関連する関数のどれが
  足りなかったかを契約に足す。
